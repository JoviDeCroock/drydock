# Guided publisher setup

Organization owners and admins can open **Settings → Integrations → GitHub App → Set up a release workflow** to inspect an installed repository and prepare a draft pull request. One explicit action authorizes repository inspection, proposed workflow/script edits, independent review, and automatic draft PR creation. Maintainers review the resulting diff in GitHub before merging.

## Repository agents

Publisher preparation uses GLM 5.3 Flash with native function tools and separates source investigation, implementation and independent review. It can list directories, read pinned regular UTF-8 files individually or in bounded batches, inspect cached source/change inventories and remaining repository budgets, search literal text in selected files, stage new file contents, make revision-checked edits, inspect the proposed diff, run static validation, and submit the complete change. It discovers the repository's actual release scripts, manifests, workspace configuration and lifecycle hooks; there is no fixed helper or repository template.

Tools operate only on the installed repository at the inspected commit. Paths cannot select another repository, ref, URL or local filesystem. Git tree modes and blob identities prevent symlink dereferencing. Edits remain in a private workspace and do not write to GitHub. Creating a new file requires a read proving that path is absent; editing an existing file requires its current read revision. Concurrent calls serialize and reject stale edits.

The agent follows repository-specific publishing behavior, including Changesets versioning, custom package selection, builds and packing, staged versus direct publication, access/dist-tags, and Git tags/releases. Its prompt provides investigation and editing recipes rather than prescribed release code. Generated scripts are ordinary files in the draft PR, with original/proposed contents visible in Settings.

An independent judge gets a fresh conversation, the frozen change digest, its own read-only repository tools, and paginated full before/after diffs. It must inspect every changed file completely before recording a pass. It can follow original and proposed call paths to assess build-before-gate, exact artifact publication, credentials, package selection and release semantics. The judge cannot edit files. Its verdict binds the same digest submitted by the drafter; a changed workspace invalidates the review.

Neither agent has a shell, dependency-install/build capability, repository imports, arbitrary network access, or a GitHub mutation tool. Drydock never executes inspected repository/package code or generated scripts. Static validation checks observable facts such as YAML syntax (no aliases), unchanged triggers and workflow defaults, secret references already present in the selected workflow (read from parsed strings, so YAML escapes cannot hide an expression), a literal protected environment, and known publishers outside the gate. Because repository text can steer the agents, it also limits what a drafted change can do:

- Files: only the selected workflow changes; supporting files are new `.mjs`, `.cjs`, `.js`, `.sh`, `.py` or `.json` files under `.github/` outside `workflows/`, `actions/` and any directory with an `action.yml`. Existing files, manifests, lockfiles, registry configuration, `.gitattributes` and CODEOWNERS stay unchanged, because other CI (including review-triggered workflows and services that ignore `[skip ci]`), hooks and package managers can run or reinterpret them before review; nothing can already reference a new file. A selected workflow that runs on `pull_request_review` events is refused, since those run the PR's own workflow before review. Changed paths use `[A-Za-z0-9._@+/-]`.
- Actions and images: no new actions beyond those the inspected workflows use plus `actions/*` and common release setup actions; new references use a release tag (`v4`, `release/v1`) because a commit SHA can name an imposter commit in a fork. Container and service images must already appear in the inspected workflows. `secrets: inherit` is refused unless the original job already had it.
- Permissions and credentials: `id-token: write` only on the protected job (never workflow-wide, never on a drafted unprotected job, so build-job attestations or Sigstore signing jobs are refused), no write scope the original workflow did not already grant, and registry tokens (`NPM_TOKEN`, `NODE_AUTH_TOKEN`, PyPI, `VSCE_PAT`, …) only in the protected job. `GITHUB_TOKEN` is always allowed.
- Protected job: an allowlist. It runs on a GitHub-hosted label (or its original `runs-on`), downstream of an unprotected producer that uploads the named candidate, and downloads exactly that current-run artifact into one dedicated directory so candidate files cannot overwrite the checkout or supply `.npmrc`/`uv.toml` configuration. Actions are limited to checkout, toolchain setup, the download, `pypa/gh-action-pypi-publish` and `changesets/action`, each with allowlisted inputs; other actions the original workflows used are allowed only exactly as they appeared there. Shell commands (including the changesets `publish` input) are limited to checksums, git identity/tag/push, `set`/`echo`, installing the publisher CLI, publisher commands whose operands are files in the candidate directory (npm `.tgz`, PyPI distributions, `.vsix`), and reviewed `.github/` scripts invoked directly from a checkout made before the download. Redirection, command substitution, `${{ }}` expressions, `$GITHUB_ENV`/`$GITHUB_PATH`, `working-directory`, containers, services, strategies, loader or package-manager environment variables (`BASH_ENV`, `NODE_OPTIONS`, `HOME`, `XDG_*`, `NPM_CONFIG_*`, `UV_*`, …), registry and config flags, and URLs that carry credentials or point anywhere but the package registries are refused. An unchanged protected job from the original workflow is left as the maintainer wrote it only when it neither publishes, holds registry credentials, nor has `id-token: write`.

It cannot prove arbitrary script semantics. The judge and maintainer review remain necessary, and a draft PR does not establish that a release is protected.

## Durable execution and budgets

Preparation returns `202` with a job ID; the browser polls its creator-owned status and resumes pending work after refresh. Cloudflare Workflows checkpoints pinned source reads, individual drafting/reviewing turns, validation and PR creation. A turn loads private state, runs the model and tools against a local copy, and saves the complete transcript/workspace atomically before the checkpoint. Failed calls cannot persist half a turn. Native model context is replayed unchanged in GLM's expected field across tool turns and remains private; it is never mixed into visible assistant text. Workflow parameters/results contain only opaque job IDs and completion metadata, never source or conversations.

Source, proposed files, transcripts, tool results, feedback and verdicts remain in organization-scoped private R2. D1 stores request/authorization metadata, safe status/failure codes and one-day expiry. Gateway payload logging is disabled. Account/organization deletion and the scheduled retention sweep remove private job data. A late write cannot revive a revoked, expired or deleted job.

Limits include two in-progress jobs per organization (a third draft request returns `409 setup_jobs_busy`; jobs older than 30 minutes no longer count), 64 drafting turns, 48 judge turns, 180 seconds per model call, 20 minutes per job, 1,500,000 cumulative input tokens and 80,000 output tokens. Drafting stops at 12 minutes, 900,000 input tokens and 56,000 output tokens so the rest stays reserved for the judge, which must page through every changed file and re-sends each page it has read on later turns; the judge stops at 18 minutes so PR creation has two minutes. Static validation therefore also caps a proposal at 10 review pages of 12,000 characters, counting the larger of each file's original and proposed text. Directory listings share one 2,000-entry limit between the agent tools and PR creation, and a path that differs only by letter case from another entry is refused because it collides on case-insensitive checkouts. Each agent's repository tools allow 200 requests and 2 MiB of decoded source. Files are limited to 64 KiB; a proposal can change the selected workflow and up to 12 supporting files, with 256 KiB of proposed content. Discovery/diff tools paginate results. Each model turn includes the remaining time, turn and token allowances. Investigation follows the release call graph and ignores repository agent instructions and unrelated product documentation. After 12 drafting turns without a changed file, the investigation can only hand off a source-grounded advisory plan or report a blocker. A fresh implementation agent receives that plan and whole pinned source files in a 96 KiB source bundle; omitted files remain readable. The investigation transcript stays private and is excluded from active implementation context. Shared time, token, source and edit budgets carry through, and tool choice remains automatic. The editor reads current revisions, changes ordinary files, validates and inspects the diff, and submits it for independent review. Reaching a budget or encountering missing evidence stops preparation with feedback rather than inventing repository behavior.

Each model turn is a durable step with a four-minute deadline and at most one transient retry. Calls are clipped to the remaining time/output allowance; completed usage and elapsed time are checked before accepting a terminal result. The shared clock starts at job creation, including source inspection. The 20-minute limit and the AI killswitch apply until PR creation starts; access and the killswitch are checked again before its first GitHub write, after which the stage (bounded by its own step deadline) is never failed for time or the killswitch, so an existing branch or PR is never reported as a failure to start over. Invalid arguments or static failures return tool feedback for correction. The agent can explicitly report a blocker. Negative judgments and unfinished work open no PR. The browser stops automatic polling after prolonged failures and offers a resume action; the repository, workflow, ecosystem and environment stay locked while a job is pending. **Cancel preparation** marks the creator's job failed, deletes its private payloads and terminates the Workflow; the checks before every GitHub write make the cancellation binding. Cancellation is refused atomically once PR creation has started; the browser then follows that job to its pull request, and a finished job keeps its pull request.

## Prefix caching

System instructions, tool definitions and existing conversation messages remain byte-stable within each agent phase. Current budgets and progress guidance are appended at the end of the conversation and checkpointed with its native results; the next request extends that prefix. Source investigation, handoff, implementation and independent review are intentional cold boundaries with separate stable affinity keys.

The native Workers AI `x-session-affinity` header is derived from an opaque job scope, agent role and model, and is stable across retries and state reconstruction. It contains no repository, organization or user labels. No additional KV or binding is needed. Gateway full-response caching remains disabled with `cf-aig-skip-cache: true`; that is separate from Workers AI prefix caching. Payload logging remains disabled.

Private state and operational events record numeric cached-input usage when the provider reports it. Missing cache usage stays unknown; all input still counts against the shared work budget. Affinity improves cache-hit likelihood but does not guarantee retention or a hit. See [Workers AI prompt caching](https://developers.cloudflare.com/workers-ai/features/prompt-caching/).

## Draft PR creation

Successful preparation rechecks the submitted digest, static validation, matching independent assessment, creator membership/verified-email policy, organization installation, AI killswitch, expiry and pinned source. These checks run immediately before GitHub mutations too. The persisted `createPullRequest: true` marker is required; old requests/jobs without it cannot begin writing.

Write permission is checked from the installation's granted permissions before spending model work; only PR creation mints a write token, and source reads use read-only tokens. Tokens remain repository-scoped on `api.github.com`; redirects are refused. Contents, Pull requests and Workflows write permissions must already be granted by the App operator and installation owner. Drydock never expands those grants.

All proposed files are committed atomically using a Git tree and commit rooted at the pinned source revision. Existing file modes, original blobs and before contents are verified. A stable branch derived from the complete change set permits bounded recovery after an uncertain response; recovery verifies every changed path and byte and refuses collaborator edits. Individual HTTP mutations are not blindly retried; installation-token minting, which changes nothing in the repository, retries transient GitHub failures. The write token minted for PR creation is revoked best-effort when that step ends. New and recovered PRs share one idempotent audit identity containing repository, environment and PR number only.

The setup branch is created at the pinned base and then moved to the setup commit, so `create` workflows see only reviewed base contents. The commit includes `[skip ci]`, which suppresses ordinary push/pull_request runs but does not guarantee that no GitHub automation runs. The PR body shows the agent summary in a code block and the environment name in a code span so neither can mention people or close issues. Review the complete diff before pushing a commit or re-running checks, so CI with repository secrets runs only reviewed code. The job never merges, configures Environment protection, approves a release or publishes a package.

## Finish setup

Configure the selected GitHub Environment and Drydock custom deployment-protection rule, bind registry trusted publishing to that environment, and map the repository/environment/ecosystem/artifact as a release target. Existing conflicting mappings must be removed explicitly. Run a real release and refresh setup checks. A requested workflow gate, an observed Environment rule, and a completed pre-publication review are separate states; an already-published package review does not finish publisher setup.

## HTTP contract

Endpoints require a session, verified email when configured, organization owner/admin role, and organization-scoped access. Job polling and cancellation additionally require its creator. Inspect/status allow 60/hour/organization; preparation allows 20/hour/organization; polling and cancellation share a separate 120/minute creator/organization budget.

- `POST /api/v1/github-app/setup/inspect`: installation and repository → pinned workflow inspection.
- `POST /api/v1/github-app/setup/draft`: selected scope/workflow/revision/environment/ecosystem and explicit `createPullRequest: true` → `202 { job }`.
- `GET /api/v1/github-app/setup/draft-jobs/:id`: safe progress, private feedback/verdict when available, and ready PR/file diff. Responses use `Cache-Control: no-store`.
- `POST /api/v1/github-app/setup/draft-jobs/:id/cancel`: creator-owned cancellation of a pending job → the job's current status. Setup bodies are capped at 200 KB.
- `POST /api/v1/github-app/setup/status`: selected scope/environment/ecosystem → independent configuration and scoped release-review checks.

Unexpected runtime termination is reconciled to a safe failed status without exposing runtime error payloads or overwriting a concurrent completed result. Operational events contain only allowlisted codes, stages, durations and bounded provider metadata, never source, tokens, messages or raw exceptions. Incomplete model turns record their finish status and numeric usage/duration metrics so operators can distinguish truncation from transport failures without logging content.
