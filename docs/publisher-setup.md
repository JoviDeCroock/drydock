# Guided publisher setup

Organization owners and admins can open **Settings → Integrations → GitHub App → Set up a release workflow** to inspect an installed repository and start a workflow that drafts, checks, independently reviews, and opens a draft pull request for an existing release workflow. CI publishers can enter the same flow from the first-review panel.

## Flow

1. Select an active GitHub App installation and an accessible repository. Inspection reads at most 12 regular UTF-8 `.github/workflows/*.yml` or `*.yaml` files, at most 48 KB each, from a pinned default-branch revision. Drydock does not execute source, workflows, builds, package code, or dependencies.
2. Select the release workflow, ecosystem, and GitHub Environment, then authorize creation of a draft pull request. The request returns `202` with a job id immediately after dispatch to Cloudflare Workflows. The browser polls the creator-owned job and can resume polling after a reload. No AI request runs inside the HTTP handler.
3. The durable job fetches the pinned workflow, drafts proposed YAML, applies deterministic checks, and asks a fresh model call to independently judge the original and proposed workflows. The judge receives neither the drafter's conversation nor its explanation. Write permissions are checked before the first model call. A negative assessment stops the job with actionable issues and opens no PR.
4. A passing candidate proceeds to `create_pr`: Drydock rechecks the source revision and current authority, then opens or recovers the draft PR. The ready result links to GitHub and includes the original/proposed diff and the independent assessment. Review the complete workflow change on GitHub before merging.
5. Configure the GitHub Environment and its Drydock custom deployment-protection rule, then map the selected ecosystem and artifact name as a release target. Existing conflicting mappings must be removed explicitly before remapping.
6. Run a real release and refresh setup checks. An observed workflow gate and a completed release review are separate states. Reviewing an already-published package does not complete publisher setup.

## Model and durable execution

Both drafting and judging use GLM 5.3 Flash (`@cf/zai-org/glm-5.3-flash`). The drafter returns plain YAML, avoiding JSON escaping/constrained decoding around a complete code file; the server supplies a neutral summary. The independent judge returns a bounded structured assessment. Both are advisory, use the existing AI Gateway with payload logging disabled, and have individual 180-second timeouts. Each Workflow model step has a four-minute deadline and at most one retry for a transient timeout, capacity, or provider failure. Invalid drafts and negative judgments are not retried or repaired automatically.

The checkpoint stages are `fetch_source`, `draft`, `validate`, `judge`, and `create_pr`; successful PR creation or recovery sets the job to `ready`. Workflow parameters, checkpoint results, and the final run result contain only an opaque job id. D1 stores request metadata, current status/stage, safe failure codes/messages, and a one-day expiry. Original source, the candidate, judge evidence, and signed result stay in the private artifact bucket under the organization's `publisher-setup` prefix; they do not enter Workflow checkpoint history. Completed results are returned only by the authenticated, organization-admin, creator-owned job endpoint.

Supporting evidence is read at the same pinned commit: root `package.json`, `pnpm-workspace.yaml`, `.changeset/config.json`, simple workspace package manifests, and literal `node .github/scripts/*.{mjs,js,cjs}` references in workflow steps or Changesets publish/version inputs. Git tree modes and blob identities reject symlinks before Contents reads. No scripts, lifecycle hooks, package builds, or dependency installs run in Drydock. Context is limited to 48 files, 40 workspace manifests, 24 KB per file, 96 KB total decoded UTF-8, and 160 GitHub requests. Recursive, negative, dynamic, and unsupported workspace patterns are skipped with explicit warnings. Only the pnpm `packages` list defines workspaces. A Changesets workflow with any context warning stops for manual setup rather than guessing from incomplete release evidence. This supporting text remains in the private source object, is sent as untrusted evidence to drafting and judging, and is excluded from checkpoints and job responses.

Each attempt rechecks the creator's account, current organization role, active installation, job expiry, and the organization's `ai-review` killswitch. These checks run again before storing a model result, before signing, and immediately before each GitHub mutation. The persisted `createPullRequest: true` authorization is required; earlier jobs without it stop without creating a PR. A revoked or deleted job cannot be revived by a late storage write. Account deletion removes authored jobs and their private objects; organization deletion removes job metadata and its artifact prefix. The scheduled retention sweep removes expired job payloads and then metadata in bounded batches. Expired jobs are inaccessible before the storage sweep runs.

A deployment without `PUBLISHER_SETUP_WORKFLOW` returns an actionable `503` instead of running an inline or `waitUntil` fallback. Queueing returns before GitHub writes. After successful validation and judging, the Workflow opens a draft PR. It never alters an Environment or changes a release decision.

## Changesets and multiple npm packages

Both model stages receive worked examples for a single npm package and a Changesets monorepo. The judge also receives contrasting examples of lost lifecycle builds, changed staged/direct publication, widened workspace selection, and missing tag/release behavior. Repository scripts and manifests remain untrusted evidence.

Supported Changesets flows keep the version-only action and its outputs/conditions separate from publishing. An unprotected preparation job selects eligible packages, runs existing prepublishOnly builds, and uses pnpm pack to preserve workspace dependency transformations. It uploads the exact tarballs with a bounded manifest and SHA256SUMS. The protected job downloads that bundle and invokes a canonical inline publisher through the existing Changesets action. Each tarball is published or staged with scripts disabled and its recorded access and prerelease tag; annotated tags and New tag output preserve GitHub release creation. Empty package selection skips the protected job.

The drafter uses reserved whole-scalar tokens for these programs. The server expands them into reviewed inline code before validation; altered or embedded tokens do not grant arbitrary script execution after the download. The judge sees exact canonical programs summarized by their contract. Validation requires the canonical preparation immediately before its bundle upload, rejects preparation shell/directory defaults, and preserves staged versus direct publication. Source-commit and whole-bundle hashes are verified before publishing or tagging.

These templates accept literal package names in Changesets ignore and simple workspace directories or one-level wildcards. Unsupported selection patterns, custom registries or publication directories, and arbitrary publish/postpublish hooks require manual adaptation; they are not silently replaced. Drydock never executes the preparation or publisher programs while inspecting a repository. They run only in the maintainer's CI after the draft PR is reviewed and merged.

## Draft limits and authority

The proposed replacement preserves existing triggers and separates build/package from publishing. Validation checks a producer artifact upload before the review environment, the publish job's dependency on that producer and literal environment, and a matching current-run artifact download before publishing those archives. It accepts the supported ecosystem guide shapes, including reviewed relative artifact directories, digest verification, existing action SHA pins, npm CLI setup before download, and PyPI's trusted-publishing action. Complex publishers and unsupported triggers require manual setup.

These checks and the independent model verdict do not prove arbitrary workflow semantics. Review build commands, conditions, provenance, package selection, permissions, secrets, and other release paths before merging. AI findings cannot relax deterministic checks. A draft must preserve existing secret references without introducing new ones.

The generated commit includes `[skip ci]`. Push and `pull_request` checks may need another commit or an explicit rerun before merging. The PR does not configure an Environment or enable protection rules. GitHub protects only the configured job; other workflows, manual publishing, and administrator bypass remain separate paths.

Inspection requires repository-scoped Contents and Actions read permissions. Starting setup authorizes a draft PR and requests a repository-scoped token with Contents, Pull requests, and Workflows write permissions before expensive drafting. The job reacquires that token before writing. The operator must configure these optional App permissions, and the repository owner must approve the installation update; Drydock never silently expands an installation. If write access is unavailable, the job stops before AI drafting. Approve the required optional permissions, then start setup again.

The automatic path prepares a judge-gated proposal inside the authorized job and rechecks the default revision and original blob before writing. The compatibility endpoint for explicit PR requests still verifies the v2 proposal signature, user/organization scope, and expiry; legacy unjudged signatures are invalid. A stable proposal branch recovers an existing PR or a partially completed one-file write; additional edits on that branch are never overwritten. Individual GitHub mutations are not blindly retried. The durable `create_pr` checkpoint has one bounded recovery attempt after a GitHub or network failure; it checks the stable branch and open PR before writing again. A namespaced audit key records a new or recovered PR once across checkpoint replays and repeated jobs. Credentials stay server-side on `api.github.com`, redirects are refused, and reads are bounded. The audit event records only repository, environment, and PR number.

## Setup checks and HTTP

Checks independently report the selected release target, Environment existence, this exact Drydock App's enabled protection rule, administrator bypass, and a real workflow-gated review. Target matching includes installation, repository, environment, selected ecosystem, and artifact name. History lookup is restricted to that target and organization. GitHub permission/upstream failures are errors rather than evidence of absent protection.

Every endpoint requires a session, verified email when verification is configured, organization owner/admin role, and organization-owned installation. Job polling additionally requires the job's creator. Request bodies are capped at 200 KB. Inspection/status requests allow 60/hour/organization; drafting and PR creation each allow 20/hour/organization. Polling has a separate 120/minute creator/organization budget.

- `POST /api/v1/github-app/setup/inspect`: installation id and repository → `{ inspection }`, with pinned revision and eligible workflow files.
- `POST /api/v1/github-app/setup/draft`: selected scope, workflow/revision, environment, ecosystem, and explicit `createPullRequest: true` → `202 { job }`. Queued responses contain metadata only.
- `GET /api/v1/github-app/setup/draft-jobs/:id`: `{ job }`, with status, stage, safe failure, independent assessment when available, and the signed result plus draft PR metadata only when ready. Responses use `Cache-Control: no-store`.
- `POST /api/v1/github-app/setup/pull-request`: compatibility endpoint accepting an exact signed proposal → `{ pullRequest }`, creating or recovering its draft PR. The automatic UI flow uses the background job instead.
- `POST /api/v1/github-app/setup/status`: selected installation, repository, environment, ecosystem → `{ status }` with independent setup checks.

Failed model attempts emit only model, stage, duration, category, bounded numeric provider/status codes, and an allowlisted finish reason. Logs and failure metadata never include raw provider errors, prompts, source, credentials, model text, or request/response bodies.
