# UI styling and primitives

The visual system is defined in [`DESIGN.md`](../DESIGN.md). This file documents how it is wired into the code.

## Stack

- **Tailwind CSS v4** via `@tailwindcss/vite` (registered in `vite.config.ts`).
- **Preact prerendering** via `@preact/preset-vite` for the public landing, auth, and docs pages. The client hydration gate in `src/index.tsx` must match both slashless paths and Cloudflare's canonical folder-index URLs (`/login/`, `/register/`, `/docs/`) for generated `*/index.html` pages.
- **Design tokens** declared in `src/style.css` with `@theme` — colors, fonts, shadows. Light is the default; dark mode is overridden inside `@media (prefers-color-scheme: dark) { @theme { … } }`. Every Tailwind utility that references a token (`bg-bg`, `text-ink`, `border-border`, `bg-accent`, `bg-danger-soft`, etc.) flips automatically with the system theme.
- **No CSS-in-JS.** No external utility libraries.

## Token names

Read `src/style.css` for the source of truth. Surface tokens use semantic names rather than scale numbers:

- Surfaces: `bg`, `surface`, `surface-2`
- Borders: `border`, `border-strong`
- Text: `ink`, `ink-muted`, `ink-subtle`
- Brand: `accent`, `accent-hover`, `accent-soft`, `accent-on`
- Severity: `danger`, `warn`, `info`, `ok` (each with a `-soft` variant for fills)
- Fonts: `font-sans` (Geist), `font-mono` (Geist Mono)

Avoid hard-coded hex values in components. If you need a value that does not exist, add it to `@theme` first.

## Product copy voice

- Favor maintainer outcomes over implementation mechanics: “review staged releases”, “release evidence”, “safety report”, and “risky changes” read better than route names, storage layers, model names, or Worker internals.
- Keep security promises concrete but user-facing. Say tokens are encrypted, hidden after save, and used only to retrieve release evidence; avoid naming internal gateways/sandboxes unless the screen is explicitly technical.
- Reserve implementation-specific labels such as D1, Dynamic Worker, Workers AI, Drizzle, and model names for docs, logs, or developer-facing diagnostics.
- Use “review” for the product workflow and “scan” only where it refers to API objects, code, or existing technical data models.

## Component prop conventions

- Always type `class?: string` explicitly (do not spread Preact's `Signalish<string>` into `cn`).
- Variants are string unions, not booleans (e.g. `variant: "primary" | "secondary"`), to keep call sites readable.
- New primitives go in `src/components/`, are re-exported from `src/components/index.ts`, and prefer composition over configuration sprawl.

## Release diff workbench

The scan detail page (`src/pages/Dashboard/ScanDetail/index.tsx`) hosts the release diff workbench. The layout is intentionally document-shaped rather than dashboard-card-heavy:

1. Completed reports lead with a compact recommendation block: block manual approval, review carefully, package context only, or likely safe. The recommendation is derived from persisted release risk rather than deterministic finding count alone, so a complete assistant review that raises release risk cannot be shown as clear just because deterministic release-delta findings are empty. Its copy keeps npm approval outside the product.
2. The report summary is a compact badge row plus mono metadata line. Summary tiles are avoided here so status, stage ID, file counts, assistant assessment, and report version do not compete with the diff.
3. The detail API returns persisted `scan_events`, but the current workbench does not render a timeline yet. When added, it should use compact timestamp + badge rows so users can see queued, started, npm access, retry, failed, completed, and decision milestones without turning the page into an audit-log table.
4. A `VersionPicker` sits in a simple bordered toolbar. Default selection is `defaultPreviousVersion` returned by `GET /api/v1/scans/:id/versions` — the version the scan was originally diffed against. Switching the picker triggers an on-demand fetch of that version's tarball via `GET /api/v1/scans/:id/compare?version=...`. Results are cached per version in component state so toggling between two versions does not re-spin the sandbox Worker. The compare response returns server-derived finding annotations for that baseline while keeping previous file text behind the per-file lazy endpoint.
   - If version metadata cannot be fetched, show a recoverable `Alert tone="warn"` in the same report position even when the picker never rendered.
5. The main workbench is `FileTree` (left, 300px) + `DiffView` (center). The tree is built from either the persisted `summary.diff` (for the default comparison) or from `createPackageDiff(compare.files, stagedFiles)` recomputed client-side when the user picks a non-default version. The tree defaults to changed files only, with a text filter and a checkbox for showing unchanged files.
6. Risk signals render below the diff and are annotated with the file's diff status plus a best-effort line number when the deterministic rule can locate the evidence in the staged text sample. The scan detail API returns both full-artifact risk and release-delta risk after a report is complete; new scans persist per-finding release annotations so modified files can distinguish findings on added hunks from findings on unchanged lines. The page leads with release-delta risk and groups unchanged or otherwise contextual signals under "Package context" so deterministic full-artifact findings stay visible without dominating a harmless release diff.
7. Persisted report sections (reviewer notes and manifest changes today; report fingerprint/provenance later) follow as section-label blocks, not cards. The old "Changed files" table was retired — that information is now available in the tree.

The `compare` endpoint resolves the chosen prior tarball from registry metadata, fetches the published `.tgz` in the parent Worker with the same registry-origin credential guard used by the scan baseline path, then parses the bytes in a credentials-free inline sandbox. Returned file samples are redacted with the same helpers used at scan time. No schema or scan-pipeline changes are involved — the feature is a read-through view on top of existing data.

## Surface-density guidance

Use cards for interactive containment and lists that need table-like edges. Prefer section labels and mono detail lines for read-only metadata. Hairline rules belong in exactly two places: the trailing rule on a `SectionLabel`, and per-row `border-b` separators inside a genuine table/list. A `SectionLabel`'s trailing rule already divides the section, so never stack a `border-t`/`border-y` immediately above or below it — that reads as a double border. The `CollapsibleCard` header is divided by its title's section-label rule alone (no content `border-t`). In particular:

- Saved scan reports and immediate review results use badge rows + mono metadata instead of grids of `SummaryCard`s.
- Empty findings do not get full bordered panels; represent them as compact badges or `EmptyLine`s inside an existing section.
- Dashboard order follows user intent: recent reviews first, workspace setup last. Stage IDs are no longer requested by hand — the 15-minute auto-discovery cron and the "Check npm" button in the recent reviews header are the only entry points.
- Open staged publishes are not displayed directly. Discovery starts scan records for newly found stage IDs, returns package/version metadata for those started reviews, and those records appear in Recent reviews.
- The recent reviews list paginates with `GET /api/v1/scans?cursor=…&filter=…`. The default filter is `undecided`; filter chips (Undecided / Approved / Blocked / All) sit above the table and re-fetch on change. Completed rows lead with release risk and changed-file count. Retries appear as separate rows — the old "newest-per-stage" dedup is gone now that decisions and pagination both depend on a one-row-per-scan model.
- Filter state survives navigation: the dashboard decision filter is mirrored to `?filter=` on `/dashboard`, and the scan detail page mirrors its file filter (`?file=`, debounced ~250ms), changed-only toggle (`?changedOnly=0` when off), selected compare version (`?version=`), and selected file (`?path=`). The bridge lives in `src/lib/query-state.ts` as `useQuerySignal(signal, { name, parse, serialize, debounceMs? })` — it works with any `Signal<T>`, whether component-local (`useSignal`) or model-owned (e.g. `model.selectedPath`). Writes use `location.route(url, true)` (replaceState) so they don't pollute history; URL → state syncs on every render so browser back/forward restore the filters. `ScanListModel` owns the filter→refresh wiring as an internal `effect`, so flipping `scans.filter.value` (from either the UI or the URL) automatically re-fetches. The dashboard records its current URL in tab-scoped session storage, and the scan detail "← Reviews" link uses that stored `/dashboard?...` URL when available, falling back to `/dashboard` for direct entry.
- The scan detail page exposes the publish decision through a single `Decide` button in the top-right of the page header whenever the scan is `complete`. Clicking it opens a modal with Approve / Block buttons and an optional reason input; submitting records the decision via `POST /api/v1/scans/:id/decision`. Once a decision exists the header shows an `approved` / `blocked` Badge with timestamp next to the trigger, and the button label flips to `Update decision`. The modal surfaces the current decision, prior reason, and any save error so the audit trail stays visible without taking up workbench real estate. The dashboard exposes the same decision as a badge column. The dialog's reactive inputs — open visibility plus the save `status`/`error` signals — are read inside thin host components (`DecisionDialogHost`, `GateDialogHost`), never in `ScanDetailPage`'s body. Reading any of them in the page body re-renders the entire page, including the risk-signals list, which is one card per finding and runs into the thousands for large packages (a multi-second main-thread freeze on opening Decide or during the save round-trip). Keep dialog-reactive reads isolated to the host. (Note: a _successful_ decision still re-renders the page once because the scan data itself changes — the large findings list and file tree are not yet render-isolated from data updates.)
- Workspace setup lives on `/dashboard/settings`, split into vertical tabs whose active section is mirrored to a `?tab=` query param (so a tab is linkable and survives reload; the default `general` tab keeps a clean URL). The tabs are **General** (org summary plus, for a deletable org only, a Danger zone that deletes the organization behind a type-the-name confirmation dialog — the zone is hidden entirely for the personal workspace and for non-owners, since the action is unavailable to them), **Members**, **Notifications**, and **Integrations** (npm access appears before the GitHub App setup so a maintainer can add the release-evidence token first). Active-tab styling uses `--color-accent` per the active-nav rule. The dashboard shows a compact npm-missing callout with an explicit “Open settings” affordance when the active organization has no npm connection.
- Connection metadata is displayed as compact label/value rows, while the editable credential form remains inside a card.
- Marketing hero copy is unboxed; feature claims use cards below the headline.

## Anti-patterns

- The retired `#7c5cff` violet accent. The brand action color is `--color-accent` (`#ea580c`).
- Pill-shaped badges (`rounded-full`). Severity and status badges use 3px radius.
- Gradient buttons, gradient hero backgrounds, icon-in-colored-circle feature grids — see `DESIGN.md` for the full list.
- Decorative use of severity colors (red as an accent, etc.). Severity colors are reserved for severity meaning.
